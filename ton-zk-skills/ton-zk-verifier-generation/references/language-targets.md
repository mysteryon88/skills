# TON verifier language targets

## Tolk

Tolk is the preferred default for new work in this collection.

- An unnamed Groth16 verifier may be emitted as a flat contract with a standard getter shape.
- Supplying `--contract-name` can select a named receiver/contract shape and a suffixed getter. Read the generated wrapper/test rather than guessing the method name.
- Tolk supports typed application code around the generated boundary, but the cryptographic core may remain low-level because it mirrors TVM operations.
- Generate TypeScript wrappers from the same protocol/language selection.

## FunC

Use `--func` when the repository or compatibility baseline is FunC.

- Preserve existing TL-B/message layout and wrapper expectations.
- Avoid manually porting a Tolk verifier back to FunC; generate from the VK with the matching template.
- Test dictionary/tuple public-input representation exactly as emitted.

## Tact

Use `--tact` for the supported Groth16 path.

- Confirm installed generator support before selection.
- Treat generated verifier logic as a boundary that can be composed into a Tact contract/trait only with explicit state and message semantics.
- Do not infer PLONK support from Groth16 support.
- Tact/zkJetton examples are educational, not production approval.

## Internal messages and getters

Generated outputs may expose both a getter and an internal verification message.

- Getter: read-only/emulated verification; useful for diagnostics and tests, not state mutation.
- Internal message: executes verification in a transaction and may be integrated with state changes.
- The generator may enforce a minimum attached value. Read the generated code/wrapper and test realistic fees; do not hardcode an old example value as a protocol constant.

## Fift

Fift generated by Blueprint/Acton/Tolk/FunC compilation is build output. Do not treat checked-in `.fif` as the canonical source unless the project intentionally owns and tests it as source.

## Target selection record

Record language, template, contract name, getter name, message opcode/layout, wrapper path, public-input representation, attached-value rule, build command, compiler version, and output hashes.
